## Introduction

The **LogOn** challenge on PicoCTF introduces privilege escalation through cookie manipulation. Web applications that store authorization roles or status flags directly in client-accessible cookies are vulnerable to trivial privilege escalation attacks.

> **Challenge Description:** "The factory is hiding things from all of its users. Can you login as Joe and find what they've been looking at?"

## Solution Walkthrough

### Step 1: Open the Challenge Website

Navigate to the challenge URL. A simple login form is presented.

### Step 2: Login as Joe

The challenge description hints to log in with the username `Joe`. Enter `Joe` as the username with any password.

### Step 3: Inspect the Cookies

After logging in, open Developer Tools (`F12`) and navigate to:

```
Application → Storage → Cookies
```

Observe that a cookie is set with a value of `false`.

### Step 4: Modify the Cookie Value

Change the cookie's value from `false` to `true`:

1. Click on the cookie value field in the Application tab
2. Edit the value to `true`
3. Press Enter to save the change

### Step 5: Refresh the Page

Refresh the browser page. The application now treats you as an authorized user and reveals the flag.

## Key Concepts

**Cookie-Based Authorization Vulnerabilities:**

When authorization state is stored in a client-side cookie (e.g., `isAdmin=false`), any user can modify it using browser Developer Tools. The server should never trust client-supplied authorization data without server-side validation.

```
# Vulnerable pattern
Cookie: isAdmin=false   →   Change to:   Cookie: isAdmin=true

# Secure pattern
Cookie: session_id=abc123  (server validates this ID against a secure session store)
```

## Security Insights

- **Never store authorization state in client cookies:** Any data in a cookie can be modified by the user.
- **Use server-side sessions:** Store role and permission data in a server-side session store (Redis, database). The cookie should only contain a random, unpredictable session identifier.
- **Cookie signing and encryption:** If data must be stored in cookies, use HMAC signing (e.g., Flask's `flask.session` which signs cookies) to detect tampering.
- **HttpOnly and Secure flags:** Prevent JavaScript access and transmission over insecure connections.

---

## Conclusion

This challenge demonstrates how client-side authorization checks are fundamentally insecure. The simple act of modifying a cookie value from `false` to `true` grants full administrative access — a vulnerability that mirrors real-world cases where bypassing access controls requires nothing more than a browser's built-in developer tools.
