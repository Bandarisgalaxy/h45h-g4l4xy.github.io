## Introduction

The **Cookies** challenge on PicoCTF emphasizes how numeric session or state cookies can be predictable and enumerable. When a web application stores meaningful application state (such as a currently selected item) in a cookie as a plain numeric value, an attacker can simply cycle through every possible value to discover hidden content.

> **Challenge Description:** "Who doesn't love cookies? Try to figure out the best one."

## Solution Walkthrough

### Step 1: Open the Challenge Website

Navigate to the challenge URL. Observe the page content and interface.

### Step 2: View Page Source

Press `Ctrl + U` to view the page source. Search for any embedded clues or hints. Notice the word **`snickerdoodle`** — this is the name of the cookie type being tracked.

### Step 3: Inspect Cookies via Developer Tools

Open Developer Tools with `F12`. Navigate to:

```
Application → Storage → Cookies → [challenge URL]
```

You will see a cookie with a numeric value — initially `0`.

### Step 4: Enumerate Cookie Values

Change the cookie value incrementally from `0` upward. After each change, refresh the page and observe the response.

```
Cookie value: 0   → "That's not the best cookie"
Cookie value: 1   → "That's not the best cookie"
...
Cookie value: 18  → Flag displayed!
```

Try values from `0` to `28`. At value **18**, the application reveals the flag.

### Step 5: Retrieve the Flag

Once cookie value `18` is set, the page displays the flag directly in the browser.

## Key Concepts

**Why Sequential Cookie Values Are Dangerous:**

```
# Attacker workflow
for i in range(0, 29):
    set_cookie("num_value", i)
    response = GET("/")
    if "picoCTF" in response.body:
        print(f"Flag found at value {i}: {response.body}")
        break
```

A cookie holding sequential integer state is trivially brute-forced. Applications should never make assumptions about what values users might send.

## Security Insights

- **Never use sequential integers for access control:** Sequential IDs are trivially guessable and enumerable.
- **Use cryptographically random session tokens:** A secure session cookie should be at least 128 bits of cryptographically random data.
- **Server-side state management:** The server must validate that the user is authorized to access whatever the cookie points to, not just accept arbitrary user-supplied values.
- **Rate limiting:** Implement rate limiting on cookie-reliant endpoints to slow brute-force enumeration attacks.

---

## Conclusion

This challenge illustrates the risk of sequential, enumerable cookies. Modern web frameworks handle session management with cryptographically secure random tokens, but custom-built applications often fall into the trap of using simple incrementing integers for state tracking, exposing themselves to trivial brute-force attacks.
